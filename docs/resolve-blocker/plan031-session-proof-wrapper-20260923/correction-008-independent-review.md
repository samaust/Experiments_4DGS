## Finding-by-finding disposition

1. **Positive handshake and readiness race — resolved in the proposed state machine.** “Fixed protocol and live evidence barriers” holds the service at READY for baseline evidence and an empty same-handle live poll, and holds it again after PONG for another live poll and final live snapshot. Only a separate FINISH permits exit. This removes the former immediate-PONG-exit race and preserves the distinction between service and client/tool terminal. Fragmented READY can accumulate after the first yield instead of being rejected merely for taking longer than1,000ms. Exact input/error/EOF behavior and structured markers replace ambiguous `repr` matching. The actual program is deliberately still a required future review item; Correction007's one-line immediate-exit program is expressly superseded and must not be used.

2. **Negative baseline/event/retirement race — resolved at design level.** Each negative service holds READY before the one ATTEMPT, and holds after a typed ATTEMPT_RESULT so Main can correlate the event delta with a single creation operation while the unit remains live. A correct rejection requires both typed failure and matching cap evidence; a generic OSError is insufficient. Controlled nonzero termination follows FINISH after evidence capture. Exact phase-specific schemas, errno/class handling and the two nonzero exit codes remain to be pinned in the source-byte package. No negative probe is approved by these descriptions alone.

3. **Prelaunch task charge — explicit table and correct hard stop added.** “Prelaunch resource reservation” now counts the client, shell/transport/manager helpers, serialized observers and cleanup commands in H, includes an unexpectedly successful negative child/thread in B, and gives separate creation, held observation, fault, post-fault and cleanup peaks. Its displayed maxima satisfy `B+max(1,H)≤8`: B1/H4 gives5, B1/H6 gives7, B2/H4 gives6, and the worst listed B2/H6 gives8. The H=0 reserve is retained. Serial observers are not treated as free while the held service/client continues running.

   **Both B maxima and H maxima still need enforcement/evidence before launch.** In particular, positive `TasksMax=8` does not enforce the table's B=1 assumption; if B reached8 while H=1, the charge would be9 despite satisfying that service cap. The future exact program, interpreter/environment startup, reachable thread/child creation and host controls must establish the proposed in-unit maxima as well as outside-task bounds. Proving only an external H limit is insufficient. Any different B or H bound requires a revised table and review; transition races and startup/cleanup peaks are included. The proposal calls the table a required enforced maximum, denies its present certification, and explicitly stops before any systemd-run or observer launch. This honest stop is why the plan-only revision passes; the table is not a measured reservation or a resource permit.

4. **Service/client/observer ownership — accurately remains blocked.** The proposal still demands exact namespaces or a host-provided mapping before comparing service PID with manager MainPID, and never treats the observer handle as the service-associated tool handle. It distinguishes the broad VTE scope from the proposed unit and does not claim that sampled systemctl output supplies continuous accounting. The full first-creation-to-retirement facility for outside clients/wrappers has not been identified. Recording preexisting shared managers as baseline cannot exempt any new per-attempt helper; the exact classification and any incremental per-attempt threads must be reviewed. No successful in-unit task-cap result can clear that external gap or prove a later two-session writer/driver peak.

5. **Retention, terminal and cleanup order — repaired prospectively, with exact package review retained.** Required live snapshots now precede FINISH. The design does not rely on `--remain-after-exit`; after documented terminal it permits manager unloading only with bound unit/root/group identity, actual client wait and tracked task terminal/reap evidence. A vanished cgroup or `populated=0` is not relabeled as zombie retirement. Failed-unit evidence is saved before exact-name reset. The start-error procedure freezes names/handles/partial effects, checks the exact unit, avoids replaying a possibly successful launch, and waits for pending approval. It uses cooperative FINISH only with intact stdin association, otherwise a verified exact-unit stop, followed by terminal collection, same-unit/task requery and guarded reset-failed. Unknown identity or unbudgeted cleanup remains a stop. This needs concrete commands, error handling and evidence schemas before execution, which the final review gate explicitly requires.

6. **Unexpected successful creation — owned retirement and budget included.** The fork parent must retain PID/start identity and wait for its one child; the thread must be joined. Success of the supposedly rejected creation fails the control even if retirement succeeds. The resource table reserves B2 for that path and forbids a concurrent observer during ATTEMPT. The later exact code must define the child branch so it exits without continuing the parent's stdin/marker protocol, retain identity before fallible observation, and handle wait/join/registration failure without losing ownership. If retirement is uncertain, no next unit starts. The design now states the needed lifecycle rather than relying on a transient child's disappearance; it does not yet provide executable proof of it.

7. **Command/environment package — remaining incompleteness is explicit, not concealed.** Correction008 pins the intended service cwd, client shell/login/TTY/workdir, structured marker format, exact-name systemctl query/stop/reset templates and serialized reader role. It expressly requires a later independently reviewed expanded argv/source/environment/observer/read-command package; the minimal environment, reader implementation, final unit names, interpreter/source hashes, output caps, phase detail fields and exit codes are not invented by this review. The candidate manager-provided metadata must be validated against exact allowed informational lines rather than ignored as arbitrary extra output. The same package must specify partial-start reconciliation and scoped permission retry behavior, with no blind service creation replay. Because the proposal identifies these as pre-execution requirements, the remaining details do not contradict its blocked-plan verdict. They prevent executable-probe approval today.
