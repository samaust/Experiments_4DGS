## Issue-by-issue assessment

1. **Writer lifetime/capacity — design choice resolved; feasibility unproved.** `W/correction-003.md`, “Lifetime, identities and charge,” now selects a writer that terminates before ADMIT, distinguishes writer and driver handles, counts all writer/transport threads and descendants in H, and rejects uncertain ownership or peaks. That is the correct scope boundary for retaining the later H=0 census in `scripts/vipe_benchmark/s1_helper_session.py` (`creation_identity_snapshot`, `owned_workload`) and `s1_validation_capture.py` (runner creation). The writer's startup and before/after-frame snapshots alone do not prove continuous absence of transient threads/children or the retirement of an external transport wrapper; exit0 of one tool session is not automatically evidence for every charged identity. The proposal correctly leaves those questions as stop gates. Concrete review must identify the complete creation/retirement mechanism, including writer startup before the driver exists, actual B/H reservations, namespace visibility, and transport-shell disposition. `R/plan049-correction-008.md` §1 currently forbids the extra writer and §4 requires H=0; only explicit new trust/topology authorization can change that pre-admission rule.

2. **Retirement/hash chronology — resolved in the proposed dependency graph.** “Lifetime, identities and charge” and “Exact v2 schema and acyclic authority” distinguish immutable exit **intent** from the subsequently observed terminal return. The writer saves proof/admission before FINISH, admission is its last write, and Main must observe the writer's actual terminal exit0 before ADMIT. The proof does not hash a fictional future exit or its own admission. Separate post-driver archival preserves the one-way graph. This is a coherent refinement of the earlier finding: the admission file exists while the writer is live but its H=0 field is expressly a prospective ADMIT condition. Adoption must explicitly authorize that interpretation. The planned driver “writer-retired gate” can validate a trusted Main handoff/intent, not independently query the tool return; source and reporting must retain that limitation. Exact durable terminal/send archival and correlation still require review. Loss of later archival correctly prevents final acceptance even if capture occurred.

3. **Native elapsed absence — resolved as a specification.** “Exact v2 schema and acyclic authority” chooses absent native field → timing copy `null`, accepted; present field → exact finite nonnegative int/float, excluding bool, with exact type/value copy. Malformed presence rejects. No native duration is repurposed as a call boundary, monotonic origin, or CPU measurement. This removes Correction002's contradictory absence rule. Actual serialization/validation controls remain required; the current v1 `session_proof` does not implement these new timing keys.

4. **UTC bounds — honest limitation added; authorization semantics still need a single choice.** The same section supplies within-event and across-event inequalities, rejects reversed or uncertain/discontinuous observations, and acknowledges that a forward clock step cannot be excluded with present tools. That addresses the earlier concern about accepting overlapping or unordered brackets. However, its prospective authorization still says “causal UTC bounds,” while its later rule says to call them ordered UTC observations until clock stability is independently supported. The adopted authority must choose explicitly: authorize ordered observations with no guaranteed physical-time bound, or require a demonstrated stability facility and stop without it. A user considering this proposal should not be told that physical bounds have been established. Neither numeric ordering nor tool-native elapsed metadata restores the currently required paired monotonic stamps in Correction008 §3. C2 remains unmet.

5. **Exact transport/readback — raw-escrow protocol specified; complete writer protocol outstanding.** “Frame, bytes and failure states” specifies E2 framing, 16,384 decoded/22,000 complete encoded byte limits, canonical Base64 and hash checks, exclusive/no-follow full writes and fsync/readback, and an R2 response carrying complete readback bytes. It rejects lossy JSON objects, preserves exact output, and appropriately defines “raw” as reversible serialization of the actual parsed return rather than inaccessible original wire bytes. Those changes address the earlier digest-only/parsed-equality gaps. The raw E2 payload, however, has only tool-envelope keys and a raw-escrow path token. It cannot by itself communicate the post-readback UTC observation, event, exit intent, proof, or admission that other sections require the writer to publish. The complete control/message grammar for those writes, readbacks and FINISH, plus writer-start launch-result escrow, is still unspecified. This must be supplied before implementation can be treated as decision-complete, along with output-budget enforcement, PTY/raw-mode behavior, partial response accumulation, duplicate handling and canonical path rules. The proposal openly requires capability checks on a synthetic fixture before any driver; none was performed here or authorized by this review.

6. **Same-handle failure handling — state policy improved; final recovery channel remains conditional.** “Frame, bytes and failure states” gives a fail-closed state chain, retains the actual driver handle, prohibits guessed-PID signaling, limits ABORT to one send after affirmative same-handle liveness, and requires reconciliation after an ambiguous response. It distinguishes writer and driver tool results and retains partial paths/retired indices. This resolves the policy ambiguity. Main transcript retention plus later exclusive archival is an honest fallback description, but the exact archival facility and failure schemas remain unreviewed. The later archival writer must not recursively depend on an unrecorded new terminal return to certify its own archive. A concrete protocol must state what is authoritative and how archive/readback failure blocks acceptance and future launch. There is presently no executed failure/recovery evidence, so C1/C3 cannot pass.

7. **Versioned authority/equality — largely clarified, with a current-authority correction required.** “Exact v2 schema and acyclic authority” fixes prospective amendment017 and authorization paths, keeps Correction008 hashes, names the 19-field proof, 11-field event and 22-key admission bindings, preserves readiness/handle/final-two-poll constraints, rejects mixed versions, and orders escrow → event → intent → proof → admission → later evidence without backfilling. Current `s1_validation_contract.py::session_proof` still accepts only exact v1 proof/event schemas; `no_timeout_launch` and `R/launch-049-exec.py::main` still bind corrections001–015 and the 18-key admission dictionary. They cannot accept this proposal as written under existing authority. Correction003 incorrectly calls Correction016 an “unadopted parallel-development proposal” and says it stays “historical/unadopted.” Current `plans/plan_049.md` §8 explicitly adopts it as conditional planning authority only. Correct that distinction before adoption; preserve the current runtime list until separately reviewed integration, and resolve any eventual016/017 runtime ordering against then-current authority. Concrete review must also pin schema literals, exact writer/journal/archive record shapes and complete new path-family high-water/vacancy rules, rather than infer them from prose. No new runtime authority files were created by this review.

8. **Source scope and rollback — conditional boundary resolved.** “Source boundary, rollback, and gates” limits proposed implementation to contract, driver, one R writer and additive controls inside existing methods/callbacks; it reopens authorization if writer retirement cannot be proved without capture/helper changes. It makes the inverse applicable only before accepted v2 history, retaining historical validation afterward. It preserves argv/STDIN, 78 source members, 249 methods/1,028 callbacks, deadlines, resource caps, CPU-only scope, outer terminal/retirement and no operational ceiling. Those are sound plan constraints, not verified source-preservation results. The concrete Main wrapper, serialization implementation, archive protocol, source diff and inverse still need bounded review before adoption/implementation proceeds under an explicit user grant.
