## Findings

1. **Positive transport is plausible, but the required live-poll sequence has a race.** The service prints READY, consumes one line, prints PONG and exits immediately. The specified subsequent empty polls may all see terminal state; a conforming fast service can therefore fail the required live-same-handle-poll condition. Define explicit READY → held live state → PING/PONG → held live state → separate FINISH/exit phases, or explicitly place the required live poll before PING and define that weaker test. The first option tests continued session usability after actual I/O. Keep phase transitions on the exact original tool handle. Separately define readiness accumulation: the first1,000ms return may be live without a complete READY line, which does not by itself show broken transport. No live handle, closed stdin or terminal-before-readiness is a different outcome. `tty:false` preserving writable tool stdin remains an empirical interface requirement; systemd's options cannot establish that property for the tool.

   The official v255 documentation says `--pipe` passes the client's standard descriptors to the service, `--wait` waits for deactivation and reports status, and `--quiet` suppresses informational output. Those semantics support testing this candidate, but do not promise an opaque Codex handle or a live return within a particular yield. They also mean the probe must parse client startup/termination messages separately from exact service markers, rather than mistake the combined stream for one service-only record. [systemd v255 systemd-run documentation](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd-run.xml)

2. **Negative controls cannot collect their specified live baselines/results reliably.** The fork and thread commands attempt creation immediately after printing readiness, then terminate on the expected uncaught exception. Main has no gate at which to collect initial `pids.events`, inspect TasksMax before the attempt, or inspect the unit after the expected failure while its service is live. A failed unit object persisting does not guarantee that its exited task's cgroup files remain available. Revise both controls into a gated protocol: readiness and baseline; explicit attempt trigger; typed outcome with errno/exception class as applicable; hold for post-attempt census/event snapshot; explicit finish with the expected nonzero status. Preserve actual tool output and distinguish cap rejection from unrelated OSError/thread failures. A traceback plus absent UNEXPECTED text alone is not a typed structured cause or a delta. The event increment and task outcome must refer to this one triggered operation.

3. **Probe charge must be established before launch, not discovered afterward.** “What the probe must prove” correctly says TasksMax only covers the service and admits that the control client/wrappers need a separate facility. However, the proposed first live operation already creates that outside client, and the live `systemctl`/file readers add observers. There is no explicit phase-by-phase B/H table, maximum allowed client/observer threads, trusted bound, containment mechanism or serialized creation reservation covering them before they run. Recording unknown overhead afterward cannot prove the unchanged `B+max(1,H)≤8` invariant. For example, in-unit B=8 plus one outside H=1 satisfies TasksMax8 but has charge9. Even at smaller actual B, an unexplained transient client/observer thread remains a gap. A TasksMax1 negative unit does not cap its observers. Supply the external accounting/enforcement precondition and peak budget for launch, held service, observation, fault attempt, failure cleanup and final cleanup before execution. If that facility is unavailable, stop on the precise missing capability instead of using an already-unaccounted probe to discover it.

4. **The service/client ownership boundary must be explicit.** systemd services are manager-created; the `exec_command` handle belongs to the systemd-run client tool session, not automatically to the manager-spawned Python root. Inherited I/O and wait can provide a trusted association, but a guessed PID, unit-name string or matching stdout is not an independent complete task map. Preserve the requirement to verify namespaces and bind unit/MainPID/control-group/source/command to actual handle/transcript, and specify how the client, shell, tool transport and every observer is identified from first creation through retirement. Existing manager infrastructure is not automatically the attempt's descendant tree; the design must explicitly distinguish preexisting shared infrastructure from per-attempt work without declaring unexplained per-attempt helpers exempt. Do not infer success for two simultaneous writer/driver sessions or later capture/helper creation merely from one service's successful PING/PONG.

5. **Terminal evidence retention and unit cleanup are not exact yet.** The successful positive service may be unloaded before Main can read final group files. The v255 documentation says successful transient units normally unload immediately, while failed units normally remain until reset; `--remain-after-exit` preserves a service but must be reconciled with `--wait` waiting for deactivation. Choose and review an explicit retention/snapshot/deactivation sequence rather than simply adding that option. [systemd v255 systemd-run documentation](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd-run.xml)

   “Stop/remove only the exact fresh units” is a scope restriction, not a cleanup command protocol. Specify exact service-manager operations, identity guards, state checks and order for each failure point, including client death, closed input, missing tool handle and observation failure. A zero live count or vanished directory cannot substitute for actual terminal/wait/reap reconciliation. Define how absence after documented collection is distinguished from an unrelated/missing unit, preserve original terminal and send records under the already accepted Main/tool boundary, and charge the cleanup observers. Do not clear failed unit state before saving required evidence.

6. **Unexpected successful creation needs owned cleanup in the test program.** The fork control has both parent and child print and exit without a parent `waitpid`; the thread control does not explicitly join or retain a structured outcome. A negative control must own its unexpectedly created task, identify it, wait/join it and record cleanup before reporting failure. It cannot rely on task disappearance between snapshots or on manager cleanup as an unspecified substitute. The failure path must stay within the reserved budget even when the capacity control is ineffective; reserve the one attempted child/thread explicitly. This remains a one-attempt negative test, not a retry loop or a fork-bomb test.

7. **Command/argument and recovery templates need completion.** Pin exact shell/login settings, service working directory/environment/interpreter startup policy, output limits and structured service-marker encoding. The tool's `/tmp` working directory is the client's cwd; it does not by itself specify the service's execution environment. The prose PONG representation appears escaped differently from Python's actual `repr` bytes; use an unambiguous exact byte/JSON expectation. Include exact observer/file-read and cleanup commands with their tool arguments and strict canonical ControlGroup/path checks, rather than leaving unspecified helpers to implement the read list. Resolve invalid/occupied unit names without reuse. On a suspected sandbox failure after a start request, determine whether the unit partially started before any allowed outside-sandbox retry; do not blindly replay systemd-run, and do not treat a pending approval as failure. Unknown partial effects block progression to the next unit. No operational timeout should be invented to compensate for a missing phase protocol.

## Decision and next action

Revise the probe into explicit state transitions and a finite operation table with prerequisites, exact inputs/outputs, B/H peaks, observer/client coverage, evidence capture points and cleanup for every failure edge. Establish or precisely report the missing external-wrapper facility first. Re-review that exact revision before execution. This design may then be useful for validating one aspect of service I/O/cap enforcement; a passing result still would not adopt the v2 evidence contract or authorize a Plan049 driver.
