# Independent review — Plan050 session-proof wrapper

Verdict: **revise before launch**. Plan050 preserves the intended CPU-only scope, same-session admission sequence, retirement rule, and independent runtime review, but the proposed writer does not yet establish C1–C3. C4 is a useful preflight outline but needs a complete artifact-family and writer-capacity gate. This is a static plan review only; no wrapper was implemented, no source or runtime operation was run, and no launch clearance is given. Review duration was not measured and is unknown.

| Criterion | Assessment | Required correction |
| --- | --- | --- |
| C1 — durable exact return/handle first | **Not met by the proposed procedure.** The raw return exists only in isolate memory while `JSON.stringify`, shell quoting, command construction, transport, and the Python launch can fail before `O_EXCL` persistence. The plan's oversize branch explicitly retires with only an in-memory handle. Fail-closed retirement is appropriate, but it does not make C1's unconditional durable-first claim true. | Specify and exercise the actual transport and failure states, including serialization exceptions, size overflow, partial/uncertain exclusive write, and same-handle retirement. State C1 only for successfully persisted returns; otherwise record a failed attempt and never admit. Show the original return/handle against readback, not merely parsed-object equality. |
| C2 — exact event bytes/hash and timestamps | **Not met.** Python `started` is obtained before a separate clock-command round trip, so it precedes the nested call; Python `returned` is obtained after escrow, so it follows the return. The immediate `Date` UTC observation has no paired monotonic value. These are causal bounds, not the exact Main call-boundary stamps named `started` and `returned` in correction008 §3. `session_proof` checks format/order and would accept these numbers, but that cannot establish their meaning. | Find a verified way to capture UTC and monotonic values at both actual nested-call boundaries, or obtain an explicit reviewed contract interpretation/change before using bounds as those fields. Keep unknown intervals separately. Confirm exact output-byte preservation with a real transport fixture and independent hash/readback checks. |
| C3 — independent sufficiency and unchanged limits | **Not met.** A distinct reviewer is planned, but has not reviewed a written wrapper or actual tool evidence. The proposed local Python writer is an additional process/session per event while the driver is live. Correction008 §1 says no new observer/wrapper/helper/thread/process, and §4 permits necessary evidence writes after the final poll while forbidding unrelated tool work or an alternative session. Plan050 neither reconciles that process with the topology rule nor charges it in capacity/ownership. | Have the independent reviewer assess the concrete writer topology against correction008, Plan049's `B+max(1,H)≤8`, and the final-poll boundary. If the writer cannot fit the existing authority, revise the procedure or seek a separately reviewed authority change before launch. Then review fresh original tool returns, escrow/events/proof, admission/send, and terminal evidence. |
| C4 — fresh attempt008 preflight | **Incomplete.** The plan correctly calls for fresh 78-source/authority hashes, storage, ownership/capacity, vacancy and high-water including retired007. Its enumerated high-water families omit Main event, raw escrow, send/outcome and other possible attempt-indexed records; `every required index008 path` does not explicitly cover globbed event/escrow families. The new writer process is not included in the live-resource census. | Enumerate all indexed artifact families, including failed/partial Main writer files, and reject any occupied candidate name; calculate the highest occupied index across them before selecting008 or higher. Include writer processes/sessions and unresolved partial launches in ownership and capacity. Save exact current hash/storage/process/path results and confirm the current static reviewer conclusion immediately before launch. |

The shell-argument escrow deserves a specific transport proof. POSIX argument limits apply to encoded command bytes and individual arguments, while `max_output_tokens` bounds neither the escaped JSON byte length nor the entire result envelope. `JSON.stringify` can also transform or reject values outside ordinary JSON. A small CR/LF/non-ASCII fixture and correct apostrophe quoting are useful but do not prove arbitrary exact tool output fits. The procedure must establish a conservative worst-case bound for the full command and returned envelope, independently compare the decoded output string and UTF-8 hash, and fail closed on overflow without claiming a C1 event. If arbitrary output is part of the intended guarantee, choose a transport that can preserve it without a fixed shell-argument ceiling and review its process/resource effects.

Plan050's positive protections should remain: exclusive fsync/readback records, exact same-handle empty polls, sole readiness line, fresh proof validation, no reuse of diagnostic007, no admission on uncertainty, original W/C and scenario timing, 64MiB memo and 150GiB artifact limits, CPU-only scope, and no operational timeout or attempt cap. Correction008's `session-bound/v1` trust substitution remains explicit; this review makes no independent kernel-attestation claim. Historical diagnostic005/007 records are examples and retirement evidence, not reusable session proof.
