# Wrapper correction 012 — shared logical-root ledger and terminal witnesses

**Plan-only response to the independent NEEDS_REVISION review of Correction011.** It incorporates the user's explicit authorization to count each exact outer tool session as one H job and group a launched process's descendants under that process-tree job until the known tree retires. It keeps `B+max(1,H)≤8` as a logical registered-root-job limit; this is not a kernel task/TID, cgroup, or host-load limit. This correction grants no implementation, probe, test, diagnostic, aggregate, admission, or launch clearance.

## 1. One shared ledger and reservation protocol

Before any launch, Main creates one attempt-scoped append-only ledger and holds one cross-process exclusive lock file for every ledger transaction. The ledger is shared by the outer driver, capture process, test runner, and any direct-root creator through the already-authorized attempt output directory. It contains attempt ID, schema `registered-process-tree-job/v1`, role B/H, root ID, creator process identity, parent root (or `outer-session`), state (`reserved`, `live`, `unresolved`, `retired`), creation/terminal evidence references, and the current source-set hash. Each record is length-delimited, checksummed, fsynced, and read back under the same lock before a transition is accepted. Malformed, missing, duplicate, or unreadable state is charged as unresolved; it never frees capacity.

Main reserves one H root in the ledger as `reserved` before invoking `exec_command`; that reservation covers the whole opaque session, its hidden wrappers, and the driver-to-capture `execve`. Immediately after the tool returns, Main binds the **exact returned session handle** and tool transcript to that same root and persists/readbacks the result. A `write_stdin` poll changes no reservation. Only the original handle's actual terminal return marks H retired. An invocation that loses its exact session handle remains unresolved and blocks reuse of that attempt/capacity.

The capture process reserves the separate B capture-runner root under the same interprocess lock **before** calling `Popen`. It atomically reads all reserved/live/unresolved roots, evaluates `B+max(1,H)≤8`, writes and reads back the reservation, then starts the runner and binds its retained `Popen` identity. A definite creation failure may retire the reservation only when the call's exact result proves no child was created. If creation outcome is ambiguous, the reservation remains unresolved. `Popen.wait()` is necessary but cannot retire the root until its known descendants also have terminal evidence.

Every reviewed direct process/thread start goes through the same serialized ledger transaction: reserve and read back before the creation call; bind its returned handle/identity immediately; preserve the charge through matching wait/join and tree retirement. The ledger lock covers only state transitions, never a blocking wait. Concurrent direct starts cannot both spend the same free slot. Start, identity, registration, census, wait, join, or cleanup ambiguity keeps its reservation charged and prevents any start that could violate the formula. At H=0 preserve the mandatory one-slot reserve; B may not reach eight.

Ledger path selection is phase-aware and must be included in the fresh output-vacancy preflight. Its directory and lock are created only after attempt-index vacancy is proved and are subject to the 150 GiB artifact cap. Use only existing session/process infrastructure: no helper observer, daemon, extra process, or thread. If the target filesystem cannot provide the required cross-process lock, fsync, and readback semantics, mark the facility unavailable and stop without launch; do not silently weaken atomicity. The implementation must independently validate crash/partial-record recovery from saved synthetic file fixtures before a live diagnostic is considered.

## 2. Creator-context map is normative

The role comes from the **actual creator process and thread at the creation point**, not a function/event name or inherited environment variable. Before implementation, the independent source map must list each concrete source line, actual creator identity/context, parent root, role, pre-reservation point, returned handle, descendant attachment point, and terminal method. At minimum, it must resolve:

| Creation site/context | Ledger classification |
| --- | --- |
| Main invokes outer `exec_command`; driver then `execve`s capture | One H outer-session root, no second root at `execve` |
| Capture process directly calls `Popen` for the test runner | New B root reserved in shared ledger before `Popen` |
| Main test-runner process directly creates a supervisor worker, declaration-script child, fixture/race/helper process, or explicit thread | A new root in its frozen B/H role; reserve each separately |
| `Owner` execution thread, explicitly started by the main runner using `_thread.start_joinable_thread` | A distinct H thread root; ambiguous creation stays reserved/unresolved |
| `Owner` thread directly starts work/sample processes via `os.posix_spawn` | Each a separate H process root, not folded into Owner's thread root |
| A process already inside a registered root starts an internal child, including L35's detached descendant or a nested helper child | Same process-tree root; record identity as a descendant before parent can exit; no additional slot |
| Internal/native thread inside a registered child process | Same process-tree root; no claim or count of its physical TIDs |

The shared `fixture_process_launch` wrapper must receive or derive authenticated creator context from the calling process's ledger registration. Main-runner callers and executable scenario-worker callers therefore make different transitions even though they call the same Python function. Unknown creator context is a hard gate failure before the launch. Any newly discovered direct Main start is added to this map and charged before use.

## 3. Tree membership and release evidence

Each root has a set of known descendant identities. The process that creates a descendant records its complete identity (boot ID, PID, start ticks, PGID and available ancestry) in the shared ledger immediately after creation and before it can release/exit; its parent root remains charged during this handoff. A child-creation ambiguity, failed identity read, or inability to persist the identity makes that root unresolved. Cross-process registry snapshots are not interchangeable with ledger root accounting: snapshots can supply identity/lineage evidence but do not independently retire a root.

A direct child is closed only with its matching retained handle's actual terminal result (`Popen.wait`, owned matching `waitpid`, or exact joined thread handle) plus closure of its descendant set. A reparented descendant is closed only by a retained, identity-pinned terminal witness acquired while it is alive and linked to the root. PID absence, PID reuse, a parent wait, Consumer/progress acknowledgment, scenario success, and unjoined thread state are not terminal witnesses. If any known descendant lacks a terminal witness, the root stays charged/unresolved and no successful aggregate/admission is recorded.

For L35, after the worker reports the detached child's boot/PID/start identity and while it is still live, the authorized main-side owner opens a Linux pidfd for that PID and immediately rereads `/proc/<pid>/stat` to bind the pidfd to the reported start ticks; mismatch or disappearance is ambiguous and keeps the root unresolved. Main retains the pidfd across worker exit, polls that exact process's terminal state, and records a final identity reconciliation. The existing worker protocol and original behavioral deadlines remain unchanged; pidfd observation must fit inside them. This does not add a helper process/thread. If pidfd support, identity binding, polling, or final reconciliation is unavailable or ambiguous on the supported environment, retain the worker root as unresolved and block the complete aggregate; do not substitute Consumer acknowledgment or relax L35 assertions/deadlines.

The source review must verify the exact pidfd ownership/closure path and no descriptor leaks. A synthetic CPU-only fixture must show the retained pidfd becomes readable when the original child exits after its leader has exited/reparented, that an unrelated/reused PID cannot satisfy the witness, and that absent/ambiguous terminal evidence keeps the root charged. The fixture may be run only after the amendment is independently reviewed, adopted, implemented, source-reviewed, and fresh preflighted under the later gates; this plan itself authorizes no run.
