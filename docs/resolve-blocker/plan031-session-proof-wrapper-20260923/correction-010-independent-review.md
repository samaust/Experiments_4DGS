**Verdict: NEEDS_REVISION.** Reviewed `correction-010.md` at exact SHA-256 `9339b6f79ffb1c7f8822752645ea82c27dbb5edae61acef5b69d8ebeeb630a67`. No source or test was edited, imported, or executed; no probe, tool session, service, diagnostic, or aggregate was launched.

The proposed `registered-job/v1` unit is coherent as a *logical* accounting model. The one H charge for the exact outer `exec_command` session covers its tool/shell transport and the driver-to-capture `execve` identity; `execve` replaces that process and creates no second B job. Capture's independent `Popen` runner is correctly a separate B job. A `write_stdin` poll on the same handle creates no new session job. The proposal correctly disclaims a kernel TID, host-wide, or hidden-wrapper limit; internally created native-library threads are included in their enclosing process job only under this expressly changed unit. This does not erase Plan049's full OS-task requirement until Main adopts an exact, authorized resource-bound amendment.

1. **The mapped explicit thread creation path is missing.** `scripts/vipe_benchmark/s1_helper_session.py:893` starts the real Owner thread with `_thread.start_joinable_thread`, and L36 deliberately exercises ambiguous native start. Correction010 inventories and gates `threading.Thread.start()` but neither names nor classifies this actual `_thread` path. It is an explicit Main-runner-created job, not an unobservable internal library thread. The revision must reserve before this call, retain the returned joinable handle or uncertainty on an ambiguous result, count its B/H role through cleanup, and release only on its exact join/terminal proof. Audit other explicit `_thread` or native starts in the mapped source before calling the creation-site table exhaustive.

2. **The child-to-Main gate has no implementable bootstrap or handle handoff yet.** Capture's runner is created at `s1_validation_capture.py:58`, before the runner-local `InvocationRegistry` exists; current capture only does a local census/check and registers after `Popen`. Main must own its B reservation before this edge, but correction010 specifies no concrete Main-to-driver/capture channel, pre-reservation, grant/failure protocol, or terminal reconciliation for that first child. Owner uses `os.posix_spawn` with the existing fd100 role channel; fixture descendants arise inside that helper and inside supervisor workers. A process-local registry cannot serialize those creators with Main merely by inheriting a descriptor. The proposed `RESERVE → grant → create → return exact handle → bind` sequence must identify its endpoints, descriptor inheritance and framing, parent-exit/race behavior, and how a process/thread handle is represented or transferred. A child cannot pass a Python `Popen` or `_thread` handle as an ordinary descriptor message. Plan048 forbids extra transport and freezes capture/runner; Plan049 permits capture changes only for no-timeout mode. The required new control path and scope amendment must therefore be explicitly authorized and reviewed, or the design must use existing approved channels without changing their behavioral contract.

3. **Detached retirement remains conditional, not specified for the existing L35 path.** `test_l35_exited_leader_live_descendant` launches a descendant from a worker that then exits; ordinary Main/runner `waitpid` cannot reap that reparented grandchild. Plan049 §4.2(9) also requires retained full identity through actual Consumer acknowledgment, reconciliation, fallback, and freeze, as exercised by `worker_detached_identity`. Correction010 correctly distinguishes a progress acknowledgment from process death, retains the H charge across reparenting, and rejects PID reuse or a missing `/proc` row as release evidence. Yet it defers the decisive retained pidfd/reaper handle, exact identity binding and terminal proof to later source review. Specify how the existing fixture gives Main a valid handle before parent exit, how its exit is established without an extra process/thread or altered scenario, and what happens when transfer/registration fails. Until then, the logical H slot must remain unresolved; no successful capacity or complete-cleanup conclusion can be drawn for that path.

4. **The role and arithmetic rules are promising but cannot yet be verified at every actual transition.** The proposed table assigns capture runner, supervisor worker and direct scripts B; Owner helpers, fixture/race workers, sentinel and detached descendants H; role persists after parent exit. The serialized gate's use of live, reserved and unresolved charges prevents two concurrent starts from spending one slot. At H=0, `B+max(1,H)` reserves one H slot; starting the first H leaves the charge unchanged, starting another H increases it, and B admission must re-evaluate the same formula. Retiring the last H returns to the mandatory reserve. The plan should state these transition cases and bind each real creation site, including Owner's `_thread` start, capture `Popen`, `Owner.spawn`, `supervisor` `Popen`, direct scripts, L18 sentinel, helper/race/scene fixtures and both detached creation forms, to an exact B/H role, reservation owner and release event. A returned PID is not automatically a transferable waited handle; registration and cleanup failures must remain charged until matching evidence. This is required before a PASS on the reservation invariant.

C3 independent sufficiency of an implemented wrapper, resource accounting, ownership and evidence remains **not met**; this plan review is not that runtime/source review. It retains original W/C, protocol and scenario deadlines, unchanged collected workload and numerical artifact/memo limits. The changed resource unit requires Main's explicit adoption and matching validator/receipt language before it can replace Plan049's original OS-task interpretation.
