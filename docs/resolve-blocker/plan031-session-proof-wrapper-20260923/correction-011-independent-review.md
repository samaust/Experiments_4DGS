The proposed `registered-process-tree-job/v1` unit reflects the user's chosen logical boundary: one H job per exact outer `exec_command` session, with descendants grouped under the launched process job. It expressly disclaims a kernel-task, TID, cgroup, or host-load ceiling. The outer driver-to-capture `execve` does not create a second root; `write_stdin` on that session does not create one either. Capture's `Popen` runner is an expressly separate B root. Owner's `_thread.start_joinable_thread` is an explicit H root, not an internal native-library thread. Its ambiguous L36 start must remain charged. Owner `os.posix_spawn` work/sample children, L18 sentinel, and main-runner fixture/race/helper children fit H; the supervisor worker and direct declaration scripts fit B. A descendant launched inside the worker, including L35's detached child, belongs to the worker's existing root and does not add an H slot. The nested helper child similarly belongs to its launching process root. Internal/native threads inside a child and hidden tool transport threads add no logical slot under this chosen unit, and their physical multiplicity is unknown. These classifications avoid double-counting if creator *process identity*, rather than merely a shared function name, determines the root.

The arithmetic is coherent for **live + reserved + unresolved root jobs**. The gate must evaluate `B+max(1,H)≤8` atomically before each start. At H=0, one mandatory H slot remains reserved and B cannot reach 8; the first H root uses that reserved capacity, later H roots increase the charge, and retiring the last H restores the reserve. A returned handle must remain charged through matching wait/join and descendant-tree retirement; ambiguous creation, registration, census, cleanup, or terminal state cannot free or reuse its charge. The existing `InvocationRegistry` and `owned_workload` currently count process TIDs, so they are source for identity/lineage only, not an implementation of the proposed root-job arithmetic.

1. **The reservation owner and first capture edge are still unspecified.** `s1_validation_capture.py` creates its runner with `Popen` before the runner-local `InvocationRegistry` exists. The proposal calls that runner a Main-owned B root, but its in-process registry lock cannot atomically serialize this start with the H outer-session charge held by Main or with other outer sessions. It does not say whether Main pre-reserves B before the outer launch, how that reservation binds the exact later `Popen` outcome, or how failed/ambiguous capture creation is reconciled without freeing a possible live root. Specify the ledger owner, scope and admission/terminal evidence for this exception. A runner-local lock can serialize its own explicit starts, but it cannot by itself enforce a global Main-owned sum across processes/sessions.

2. **Creator-context mapping is required to make the tree rule unambiguous.** `fixture_process_launch` is used both in the main runner and in executable worker code. Its main-runner calls create independently charged H roots; its nested/L35 calls create descendants of the worker root with no new slot. `Owner.spawn` runs in a Main-runner-created Owner thread and starts separate H process roots; it must not be folded into the Owner thread's H slot. The row for “each distinct process started by the current main runner” should explicitly include the capture runner exception and identify process, thread, and parent root at each creation site. The promised later source map is a valid gate, but the plan should make this context rule normative so that a shared creation wrapper cannot classify by event label alone.

3. **L35 has no specified exact terminal witness.** `test_l35_exited_leader_live_descendant` creates a child within the scenario worker, records its PID, allows the worker to exit, then verifies the child is still live. The main runner can wait for the worker, but cannot ordinarily `waitpid` the reparented grandchild. `Owner.lineage` retains boot/PID/start/PGID identity across reparenting, and `worker_detached_identity` exercises actual Consumer acknowledgment, reconciliation, freeze, and fallback. Those operations prove binding and protocol state, not the descendant's death. The proposal correctly rejects acknowledgment, leader wait, PID disappearance, and PID reuse as terminal evidence, but it does not identify an existing retained exit handle or equivalent identity-pinned terminal observation for this exact child. Specify when and by whom that witness is acquired while the worker lives, how it survives reparenting, and how failure retains the B worker root charge. If no such witness is possible within the preserved scenario/deadlines, the proposed limit can fail closed but cannot support complete retirement/aggregate acceptance.

4. **Release needs a tree-level ledger rule.** Current `retire_owned(pid)` marks a direct child retired after matching wait, and capture's `Popen.wait` proves only its runner's exit. Neither alone proves that known descendants of that root have retired. The amendment says to retain the root slot, but should define how descendant identities are attached to the root across process-local registries, how a newly discovered child is recorded before its parent exits, and which identity-pinned observations close each descendant. This is especially relevant to supervisor worker cleanup and fixture registration-failure paths. No new slot is needed for an internal child, but missing child evidence must leave its root unresolved.

These are plan-specification gaps, not a rejection of the user's logical job choice. Revise the capture reservation/ownership exception, make creator-context classification explicit, and give the L35 descendant and general tree-release path an exact terminal-evidence rule.
