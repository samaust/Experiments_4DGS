## Exact transport observations

In the `functions.exec` JavaScript isolate, a JSON-shaped `arguments`/`result` fixture was serialized with `JSON.stringify` and passed as one added line to `tools.apply_patch`. The fixture is saved as [synthetic-direct-patch-escrow-001.json](synthetic-direct-patch-escrow-001.json). Its result contains `chunk_id`, `wall_time_seconds`, `session_id`, `exit_code`, `output`, and `isError`; output is `A\r\nβ🚀\r\nquote ' and \\ slash\n`. The serialized JSON was 433 UTF-8 bytes; the patch file was 434 bytes because the patch added one final LF. A local `cat` readback matched the original `JSON.stringify(fixture) + "\\n"` exactly, and parsing the returned text matched the original output string and handle.

The output string's UTF-8 bytes were `410d0aceb2f09f9a800d0a71756f7465202720616e64205c20736c6173680a`. Its SHA-256 was `5de7a1a3a31fedc2e302ffa2d173f8973b19cfe975e060557526126279ead35b`; the saved file's SHA-256 was `f73f4ac0da3c67db74bf83072d6730209ed80911d2560e736172b0a922d8f438`. This proves this small fixture survived JSON escaping and patch insertion; it does not prove arbitrary tool return values can be serialized or that patch transport is byte safe at all sizes.

The first `*** Add File` call returned `{}`. Repeating the same `*** Add File` to the occupied path also returned `{}` rather than an existence error. Thus the exposed bridge cannot be treated as an exclusive-create primitive. Its result did not provide a created-versus-existing indicator or fsync/durable-close attestation. The only exposed filesystem readback path found in `ALL_TOOLS` was `exec_command`; the successful `cat` and `python3 -c` readbacks each launched a separate host command. No no-new-process readback was demonstrated. The `tools.apply_patch` implementation's internal process topology is opaque; this probe can say only that Main did not explicitly start a shell for the patch call.

The saved prototype passed `node docs/resolve-blocker/plan031-session-proof-wrapper-20260923/synthetic-sha256-prototype-001.js` with exit0. Hash computation is feasible in the isolate, subject to reviewing size/memory behavior before any live use.

## Timestamp facilities and contract effect

Direct `typeof` observations in this isolate: `Date`, `BigInt`, and `setTimeout` are available; `performance`, `process`, `crypto`, `TextEncoder`, `btoa`, `Atomics`, and `SharedArrayBuffer` are undefined. `Date.now()` and `new Date().toISOString()` provide UTC wall-clock observations, not monotonic readings. `clock__curr_time` provides UTC time through a separate tool call, not a monotonic reading at the nested tool boundary. `wall_time_seconds` in a returned tool result is an elapsed tool measurement, not a monotonic start or return stamp. Calling `exec_command` to read a host monotonic clock would start a separate process and bracket, rather than measure, the actual nested-call boundary.

JavaScript can sample UTC immediately before and after awaiting a tool call, but these samples bound the call; they are not exact paired UTC/monotonic `started` and `returned` observations. No exposed facility was found for an exact monotonic sample at either boundary without an extra helper process. Labeling estimates or bounds as the exact `started`/`returned` fields required by correction008 §3 would misstate their meaning even if `session_proof` accepted ordered finite numbers.
