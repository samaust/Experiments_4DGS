# Wrapper correction 009 — main-owned execution-job accounting proposal

**Plan-only proposal based on the user's explicit choice** to simplify execution limits/evidence by counting jobs created and tracked by the main runner, with each opaque outer tool session counted as one job. This changes the meaning of Plan049's resource-accounting unit; it does not claim a kernel-enforced OS-task limit. It is not adopted until independent review and Main integration, and it authorizes no source edit, probe, test, diagnostic, or aggregate.

## 1. Proposed accounting boundary

Replace the requirement for an externally managed host group to enumerate every Codex/tool wrapper thread with a **main-owned execution-job ledger**. Keep the numeric rule `B+max(1,H)≤8`, but define its unit as a registered execution-job slot rather than an OS task/TID:

- `B` is the number of live primary jobs that Main/the test supervisor explicitly starts through the reviewed process/thread creation gate.
- `H` is the number of live helper jobs plus opaque outer tool-session jobs. One outer `exec_command` session is one job from its exact call until its actual terminal return. `write_stdin` sends/polls on the same returned `session_id` and do not create another job. Do not infer a PID or number of hidden transport threads from the opaque handle.
- Every new job reserves one slot before creation. The registry retains the reservation through successful `wait()`/`join()` and actual terminal evidence. Failed registration, uncertain identity/liveness, missing terminal, or failed cleanup retains the charge and blocks further creation. At `H=0`, the formula still reserves one slot.

This explicitly stops claiming that the cap measures every host OS thread inside Codex's external transport. It preserves the eight-slot maximum for the admitted logical job model, not a bound on unrelated machine load or hidden wrapper TIDs. The user authorized that trust boundary by answering yes to counting the outer tool session as one job. Main and the independent validator must label the result `registered-job/v1`, not kernel-task accounting or a host-wide process cap.

## 2. Required Main-owned registry behavior

Before any implementation change, Main inventories every in-scope `Popen`/process creation, `threading.Thread.start`, worker/helper/sentinel/direct-script launch and detached-descendant creation path. Each must either use one shared fail-closed creation/retirement gate or be demonstrated not to create a separately charged job. Existing CPU thread environment pins remain fixed. No path may start work first and register it later.

The registry records an append-only ordered event for each job: unique job key, kind, parent job, intended role/command, creation reservation, returned process/thread/tool handle, locally available full identity (PID plus boot/start identity for OS children), start/ready state, exact wait/join/outer-terminal result, and retirement decision. OS PID remains identifying metadata where available, not a substitute for the retained process handle or tool session handle. Release a job slot only after its matching process handle has been waited, thread handle joined, or exact outer tool session is terminal. Recheck the formula immediately before and after every creation and at each existing admission/cleanup transition.

For any process that can create another process/thread, its child creation must also pass a registered gate and report the child handle/identity to its parent registry before the parent may retire. Prohibit unregistered daemonization, detached spawning, native worker creation outside the reviewed policy, and fire-and-forget threads. Where an existing test intentionally reparents/detaches a descendant, preserve the scenario: retain the original registered identity/lineage and charge until the existing Consumer/owner protocol proves the exact child has retired. PID reuse, disappearance of a direct parent, or the parent's exit alone does not release the child charge. If a required existing path cannot satisfy this registry contract without altering its behavior, this proposal is not implementable as written and the host-enforced group remains necessary.

The registry is the acceptance evidence for the logical limit; it does not periodically sample unrelated `/proc` tasks or launch new observers. Existing exact Main/tool transcript is the accepted outer session boundary. No self-reported PID admits a tool session. Preserve exact same-handle readiness, empty polls, ADMIT/send/terminal ordering and all currently required identity/freshness checks except the superseded demand for cross-session kernel enumeration of opaque wrappers.

An independent reviewer must determine whether this is a coherent, sufficiently enforceable interpretation of the user's choice; whether the existing source/test launch paths can all be mediated without changing behavior; how the current detached/reparented Consumer and native-thread paths meet the registry contract; whether any process can bypass it; and whether the retained eight-slot formula has unambiguous `B`/`H` classifications at creation, waiting, failure and cleanup edges. The reviewer must explicitly identify that `registered-job/v1` is not an OS-task or machine-wide resource guarantee. No plan/source/test/runtime change is adopted by a passing proposal review alone.

Only after those checks may Main seek the separate diagnostic launch clearance required by Plan049, then perform serial authorized diagnostics and the unchanged final aggregate.
