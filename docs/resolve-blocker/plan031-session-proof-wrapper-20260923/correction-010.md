# Wrapper correction 010 — explicit registered-job boundary

**Plan-only revision of Correction009 after its independent NEEDS_REVISION review.** The user explicitly approved this simplification: count jobs the main runner creates/tracks, and count each opaque outer tool session as one job. Preserve the numerical formula `B+max(1,H)≤8`, while changing its unit from actual host OS tasks/TIDs to registered logical jobs. This is not a kernel-enforced or machine-wide task limit. It authorizes no implementation, probe, test, diagnostic or aggregate by itself.

## 1. Exact unit and no-double-counting

The accounting unit is one **registered execution job**, not one PID/TID:

- One Main `exec_command` session is one H slot from the exact `exec_command` call until that exact returned tool session reaches actual terminal. Its shell/tool transport, driver, and the capture process occupying that same execution slot by `execve` are covered by that one slot and are **not** separately counted in B. The `session_id` is only the job handle; it is not a PID or claim about hidden wrapper threads. `write_stdin` sends/polls on that same handle and create no slot.
- Every separately concurrent process created beneath the session or by a registered process is one new job. A process replacement with `execve` keeps the existing slot; a `subprocess.Popen` child receives a new slot. Every explicit `threading.Thread.start()` receives one new job slot. Threads a process creates internally through native libraries remain part of that process job; no OS-thread cap is claimed for them.
- The capture-created runner from the existing `Popen` is one B job. Existing supervisor/scenario workers and direct-script process jobs are B. Owner helper processes, sentinels, fixture/race helpers and detached descendants are H. The outer exec session is H. Main-created threads used by primary scenario work are B; threads used only as a helper/fixture mechanism are H. Role is frozen in the launch-path map before runtime; an unmapped role defaults to H and cannot launch until mapped/reviewed. A job keeps its original role even if its parent exits or the child reparents.
- An H slot remains charged through exact tool terminal or exact process/thread wait/join, including failure cleanup. A Consumer/progress acknowledgment is not a process terminal and does not release a detached-descendant H slot. If PID/start identity is uncertain, the slot remains charged and blocks further creation. At H=0, retain the mandatory one-slot reserve in the formula.

Thus the driver/capture identity nested in the opaque session is not double-counted; its independently created runner is counted. This rule intentionally abstracts away multiple kernel processes/threads that the outer tool hides and multiple internal OS threads within one child job. All future evidence and conclusions must use label `registered-job/v1`; never call the result an OS-task count, cgroup cap, or host-wide load bound.

## 2. One serialized creation/retirement gate

Before implementation, source review enumerates every current child process, worker/helper/script/sentinel/detached-child and explicit Python thread creation site. A frozen table binds each site to B or H, parent job, handle type and release event as defined above. All listed sites use one fail-closed reservation API. The gate atomically evaluates **live + reserved + unresolved** jobs under the formula, records the reservation before `Popen`/thread start, then binds the returned handle before releasing the gate. Concurrent starts cannot reuse one free slot. On creator failure, keep the reservation until the exact failure result proves that no job was created; on successful creation, release only after the matching terminal/wait/join result. Registration failure after a returned handle retains the slot and triggers handle-specific owned cleanup; it never loses the handle or releases on PID disappearance alone.

For an existing process that itself creates a child, require an inherited parent-control channel and a synchronous protocol: `RESERVE(role, parent_job)` → main registry grants/denies one slot → child performs exactly one creation → child returns the exact process/thread handle and identity → parent registry binds it. The child may not create another task until the prior creation is bound. The channel is an inherited descriptor on an already counted process; it may not start a new broker process/thread. Every creation path inside helper, native, fixture and detached-child code must be routed through this gate or be proved unable to create additional process/thread jobs. If a required existing path cannot be mediated without changing the scenario, this proposal fails and cannot be adopted as sufficient.

For reparented detached descendants, the original registry retains the child job key, parent lineage, PID/start identity and owned handle across parent retirement. Keep it charged until the existing Owner/Consumer/fallback path supplies the required exact terminal/absence evidence for that identity; acknowledgment alone, parent exit, a missing `/proc` row, or PID reuse does not release it. If ordinary `waitpid` is unavailable after reparenting, the source review must specify a retained pidfd/approved reaper handle and the precise exit proof. If the present fixture cannot furnish that without behavioral change, retain the current cgroup/resource-group blocker rather than weaken the test.

## 3. Job-role table and evidence

| Launch path | Slot | Release condition |
| --- | --- | --- |
| One outer Main `exec_command` session, including its tool/shell transport and driver→capture `execve` identity | H, exactly one | Actual terminal result on the same tool session handle |
| Capture's existing `Popen` runner | B, one per concurrent runner | Exact returned process handle waited to actual terminal |
| Existing supervisor/scenario worker and direct declaration-script child | B | Exact returned handle waited to terminal |
| Owner helper, fixture/race worker, sentinel, or separately created detached descendant | H | Exact returned handle waited/retired; detached child also requires full retained lineage and terminal evidence |
| Explicit thread started for primary scenario work | B, one per started thread | Exact `Thread` handle joined |
| Explicit fixture/helper thread | H, one per started thread | Exact `Thread` handle joined |
| Native/runtime threads internal to an already counted process; hidden tool-wrapper threads | No additional slot under this logical model | Counted only as part of their process/session job; no claim about their number |

The role table is exhaustive only when matched to every actual creation site during source review. Any unmatched site blocks implementation and launch. Main saves an ordered registry journal with job key, parent, role, reservation-before-create, creator outcome, exact handle, identity when locally available, start/terminal/wait/join event, retained unresolved charge, and final disposition. The same outer tool transcript and handle evidence remain required. The registry journal establishes only the logical-job rule; it does not attest hidden PID/TID counts.
