# Wrapper correction 011 — process-tree job accounting proposal

**Plan-only revision after Correction010's independent NEEDS_REVISION review, incorporating the user's explicit choice to group descendants under the launched process job until the known tree retires.** The opaque outer tool session is one logical H job. Main-owned process/thread starts are tracked through retained handles. The numeric formula remains `B+max(1,H)≤8`, but it now bounds concurrent logical job roots, not kernel tasks/TIDs, hidden wrapper threads, or total machine load. No implementation/probe/test/diagnostic/aggregate is authorized by this proposal alone.

## 1. Exact accounting boundary

The unit is a **registered job root**:

- One exact Main `exec_command` session is one H job from invocation through actual terminal on that same returned tool handle. Its shell/tool transport and the driver/capture identity across `execve` are covered by this one H slot; they are not separately counted in B. `write_stdin` on this session does not create another job and a session handle is never treated as a PID.
- Each distinct process started by the current main runner through a reviewed creation site is one new B or H job according to the frozen role table. The runner retains its actual process handle (`Popen` or PID plus matching `waitpid` ownership) and waits for its terminal. `execve` replacement keeps the same job root. The capture-created test runner is its own B job; the outer driver/capture process remains part of the outer H session.
- Each explicit thread that the main runner starts is one B or H job according to its frozen role and remains charged until its exact thread handle is joined. This includes the actual `_thread.start_joinable_thread` Owner start and all `threading.Thread.start()` creation sites. An ambiguous start retains a reserved charge until the returned handle is reconciled or ownership is safely retired.
- Descendant processes and threads created **inside** a registered process job belong to that job's tree and do not consume additional logical slots. They remain part of the root job's outstanding ownership until the existing registry/lineage/Consumer/fallback evidence proves that every known descendant has actually retired. This is the user's requested simplification. It does not claim that one job contains only one OS task.
- A thread created by the main runner is its own job; threads created inside an already-counted child process belong to that process job's tree. Any direct child separately started by the main runner is a new job, even if another job is still active. Jobs retain their original B/H role throughout retirement, including after parent exit or reparenting.

Every evidence artifact and report must say `registered-process-tree-job/v1`. It must not call the eight-slot rule a kernel cgroup limit, an OS thread limit, or a host-wide task bound. The deliberately omitted quantities are hidden Codex/tool TIDs and descendant TID multiplicity inside a registered process-tree job; the user accepted an opaque outer session as one job and descendants grouped under their launched process job.

## 2. B/H role table and transitions

| Existing path | Role/slot | Counted identity and release evidence |
| --- | --- | --- |
| Main's outer `exec_command` launch, including its hidden shell/tool wrappers and driver→capture `execve` | H, one job per exact session | Exact original tool `session_id`; release only on same-session actual terminal return |
| Capture's `Popen` of the unchanged suite runner | B, one job | Retained `Popen` handle/PID identity; release after actual `wait()` plus its registered descendant tree retirement |
| Main-runner `supervisor worker` process and direct declaration-script child | B, one job per direct start | Retained returned process handle; wait/terminal, then retire all known descendants |
| Owner's `_thread.start_joinable_thread` and any explicit main-runner helper/fixture/race/sentinel thread | H, one job per direct thread start | Returned joinable handle; exact join/terminal result; unknown start remains charged |

| The L35 worker's detached descendant, a nested helper's child, or another child created inside an existing process job | No extra slot; part of that existing process-job tree | Retained full boot/PID/start/PGID identity and existing Consumer/fallback/terminal proof; the root slot remains charged until retirement |
| Native/runtime threads created inside a child process | No extra slot; part of that process-job tree | Do not infer or claim an OS TID count; process-job root cannot retire while known child work remains |

Before any code change, an independent source map must bind each actual creator and current source location to exactly one row, including capture `Popen`, supervisor worker `Popen`, `Owner.spawn`/`os.posix_spawn`, the `_thread.start_joinable_thread` start, direct scripts, sentinels, fixture/race workers, and both detached-child forms. Any newly discovered direct Main start is added as B/H before launch; an unmapped start blocks the run. The category follows the launch role; child lineage does not reclassify it.

The main runner serializes reservations under its existing in-process registry lock. Compute the charge using **live + reserved + unresolved root jobs**, not only current running handles. Reserve before the exact creation call, bind the returned handle before any fallible census/identity work, and release only after exact wait/join plus retirement of all known descendants. Start failure releases only when its exact failure result proves that no job exists. Registration, census, identity, wait, join, child-exit, or cleanup uncertainty keeps the job charged and blocks another creation that could cross eight. Re-evaluate `B+max(1,H)≤8` before and after each existing Main-owned creation and at cleanup/retirement transitions. When H falls from1 to0, retain the mandatory one-slot reserve; never allow B=8 at H=0.

## 3. Detached descendants and limits of Main's evidence

Use the existing retained ownership registry and Owner/Consumer protocol to preserve attached-to-reparented identity, including boot ID, PID, start ticks, PGID and ancestry. For L35, the main runner must bind the descendant identity while its original worker is still alive, retain it after leader exit, and preserve the root H/B job charge until exact descendant terminal evidence. A progress acknowledgment, Consumer data acceptance, original leader's `wait()`, PID disappearance without identity reconciliation, or PID reuse does not prove descendant retirement. If the current fixture/owner path cannot provide the exact retained identity and actual terminal evidence without changing its scenario or deadlines, do not claim the job is retired; keep the logical slot charged and stop further work.

This amendment removes the requirement for a dedicated host cgroup solely to account for opaque tool-wrapper TIDs. It does not waive the process-root and known-descendant identity, creation/wait/join/retirement, source-integrity or same-handle terminal evidence already required by Plan049. It accepts that descendants and their internal threads occupy one logical root-job slot; therefore no claim of hard physical task ceiling follows. The systemd synthetic probe from Correction008 is superseded only after this plan revision receives independent PASS and Main records adoption under the user's explicit boundary decision.
