## Compact but complete ledger

Use a reviewed, versioned, closed event table: literal event name, exact emitter/callsite, required/optional keys, types and finite enums, canonical identity/nonce/handle/descriptor fields, allowed state transition and one-shot operation key. Unknown keys and arbitrary nested payloads fail. Retain every event/field needed by selected assertions, replay, ownership, exact Main handle, root and descendant reservations/binds/waits/retirements, pidfd pin and signal outcomes, session terminal, failure and recovery; preserve Addendum013's full command/environment descriptor requirement in the reservation unless a separately reviewed equivalent immutable binding proves it. Keep deterministic compact UTF-8 JSONL with sorted keys and no insignificant whitespace, explicit version, newline and hash-chain framing. Remove only proven redundant/unrequired duplicate fields after a field-by-field reviewer map; no silent truncation, sampled evidence, digest in place of required detail, changed assertion, or missing failure event. A prospective audit must verify the full schema/emitter/state-machine closure, even though a cumulative theoretical byte sum is no longer a source-edit gate.

The append protocol is transactional at the **committed-prefix** level. Hold the exclusive ledger lock; reread actual file bytes from disk; verify exact canonical lines, hash chain, last committed offset and that size is already `≤8,388,608`; render the whole next event in memory and validate its schema and one-shot key. Let `S` be the verified actual byte length and `L` the encoded complete line length including newline. Reject before opening/writing for append if `S+L>8,388,608`; accept equality. Keep the same lock through a single complete write attempt, fsync, exact readback of `S+L` bytes and chain verification; mark the event committed only after readback. Recheck actual size under lock on every append rather than trusting cached counters. Never append a second event after an unverified write. The first ledger sidecar remains the driver's first filesystem mutation after read-only candidate, high-water, vacancy, host and authority checks; bootstrap is fsynced/read back before a child/admission.

Regular-file writes can short-write or error after writing a prefix. A short/ambiguous write is **not** a committed event: under the same lock, attempt rollback to the previously verified `S` offset, fsync and reread the identical prefix. If rollback/readback succeeds, retain an immutable external error report and stop this attempt; do not silently retry or omit the required event. If rollback or readback fails, preserve the file **without further mutation**, block every further append/admission/retirement, and report the last verified committed `S` and prefix hash, attempted `L`, and observed write/truncate/read errors. Report physical tail bytes, length or hash only if those values were actually read and verified; otherwise label each unknown. No recovery may reinterpret a partial tail as a committed row or overwrite prior immutable rows. Before any later recovery, an independent reviewer must identify the verified committed prefix and any uncertain suffix and authorize a correction under the existing evidence rules. Thus the cap is enforced for intended writes and no oversized or silently corrupt **committed** ledger exists; a physical partial tail can exist after an OS error and cannot honestly be promised away. If the actual file is already over cap, fail closed without further mutation. Boundary tests must demonstrate unchanged prefix on rejected over-cap append and successful recoverable short-write rollback; injected rollback/readback failure must demonstrate explicit uncertainty and stopped work.

There may be no room for an emergency ledger row at the cap. Report `JobLedgerCapError` through already permitted Main status/terminal evidence and the live return channel with last verified `S`/prefix hash, attempted `L`, operation and exact Main handle; include a newer actual size/hash only when read and verified, otherwise mark it unknown. No over-cap append or dropped event is allowed. Only an already authorized, independently reviewed existing output family may hold this report; do not create a new sidecar or relabel a path. Main must reconcile the exact owned process tree and same returned handle; unknown outcomes keep H/B charged and prohibit false retirement or another attempt. If even the external durable report cannot be written, Main reports the uncertainty in its transcript and stops. A cap hit fails acceptance; preserving the original behavior means stopping before the evidence guarantee fails, so the workload may remain incomplete. Completion of every otherwise valid unbounded run cannot be guaranteed with a fixed cap. If actual selected work needs a higher cap, Main must seek explicit numeric authorization after measuring the need; this proposal grants none.

Runtime actual-byte validation adds a second check; it does not replace this static proof.

Separately, the driver completes all read-only candidate/high-water/vacancy/host/authority and prospective C2 checks before its **first filesystem mutation**, the exclusive ledger sidecar.
