# Initial independent review — lost Main exec handle

Scope: read-only examination of the saved candidate009 launch evidence, current Plan049/Plan054 trust and ownership rules, and the exposed tool interfaces. No diagnostic session was polled, signaled, admitted, resumed, or otherwise contacted. The review used only short read-only shell inspections; no diagnostic, workload, or test was launched. Resource use of candidate009 remains unknown unless separately measured.

## Evidence and conclusion

- [objective.md](objective.md) defines C1–C4 and forbids PID-based identity recovery. [lost-handle-001.json](lost-handle-001.json) records that the nested `exec_command` returned inside Main's `functions.exec` JavaScript isolate, then `crypto` was referenced before the result or its `session_id` was saved or emitted. The outer error was `ReferenceError: crypto is not defined`; the exact nested return, including any session handle, is unavailable in that saved record. This is evidence of a lost result, not evidence that the nested command failed or terminated.
- [host-census-001.json](host-census-001.json) records a later read-only `/proc` observation: a command-line match for `launch-049-exec.py diagnostic 9` at PID/PGID 378088, state `S`, with 486 census entries and no census errors. This establishes only a host observation at that instant. PID, command line, parent, start ticks, and state do not bind that process to the original opaque exec session or prove its current terminal state. The census sent no signal.
- The locally exposed `exec_command` API returns a `session_id` for an ongoing command. `write_stdin` requires that numeric `session_id` to send or poll. `functions.wait` requires a prior running **outer cell ID**; the failed wrapper produced a `Script error`, not a running-cell ID. The exposed interfaces provide no list/get/recover-session operation, no reverse lookup from PID or invocation to session ID, and no replay of the nested return from a failed isolate. The `store`/`load` helpers work only for values explicitly stored by a script; the failed wrapper did not store the result. This is an interface inventory and inference about currently available routes, not proof that platform internals lack a record.
- [Plan054](../../../plans/plan_054.md) P2 and the [adopted trust amendment](../plan031-session-proof-wrapper-20260923/correction-008-trust-amendment-001-proposal.md) require Main to retain the exact positive returned handle on the actual return and use that same handle for start frame, required live polls, `ADMIT\n`, terminal, and retirement. The original visible tool return is the finite trust boundary; a file copy, driver self-report, or PID cannot replace it. Plan049 keeps ambiguous ownership charged, `B+max(1,H)≤8`, serial CPU-only work, and no arbitrary execution time or attempt ceiling. Candidate009 preflight was only for pre-admission proof capture. These rules do not authorize a new candidate while this ownership/retirement is unresolved.

**C1: FAIL with current exposed tools.** No authorized exact Main exec-handle recovery route was found. Do not guess a `session_id`, probe possible IDs, use PID as a surrogate, or send a start frame, empty poll, `ADMIT`, signal, or terminal request to the unbound process.

**C2: preserved at the recorded boundary.** The saved lost-handle and read-only census records preserve the launch request, wrapper exception and host observation. They record no start frame, admission, payload, test, or signal after launch. They do not prove current liveness, absence of later external activity, or terminality. Candidate009 remains an unresolved charge and its index/identity cannot be reused.

**C3: reviewable prospective sequence, not a retrospective repair.** For a future, separately cleared fresh attempt, Main should perform all source/authority/resource/high-water/vacancy checks before the launch. Use a dedicated `functions.exec` cell containing only the awaited `tools.exec_command(args)` and immediate raw-return capture: assign the returned object to a local constant, immediately call `store` under a unique attempt key with that full serializable object, then emit the full object and its `session_id` with `text`, and end the cell. Do not put hashing, UTC formatting, JSON event construction, `apply_patch`, polling, a second launch, or any other fallible work in that cell after the nested return. Check that the cell completed successfully and that the original full result and exact positive, bounded `session_id` are visible and match the stored value before any start frame. The later cell may `load` the raw value, prepare a value-preserving v2 copy, write it, read it back, and compare it to the original visible result. Every later `write_stdin` uses the retained exact handle. If storage/emission/completion fails, the attempt is unresolved; do not reconstruct a handle from a file or PID. `store` is a session-local convenience, not a durable independent attestation, and the exposed wrappers offer no atomic guarantee against failure between nested return and the first successful `store`/emit. The original visible return remains mandatory under the adopted finite trust boundary. A separate API providing atomic returned-result escrow would close that residual failure window, but is not currently exposed.

**C4: not met.** This review validates the interface limitation and the proposed ordering by inspection only. It cannot validate candidate009 terminal/retirement or perform a live same-handle sequence. Runtime resumption requires trusted exact-handle recovery or trusted retirement, followed by fresh gates and independent review; no live diagnostic or aggregate is cleared here.

## Required external intervention

Ask the Codex tool/session platform operator to correlate the original diagnostic009 `exec_command` invocation (the exact command, TTY/escalated request, and failed wrapper call) with its native session record and return the **actual returned `session_id` plus an authenticated invocation-to-session/terminal-state record**, and provide the supported means for Main to reattach or retire that exact session. If the handle cannot be recovered, the operator must identify and retire the exact platform-owned session and its process-tree job using platform ownership records, then provide auditable terminal and descendant-retirement evidence. A PID/argv match or operator assertion without the invocation-to-session correlation is insufficient. Until one of those actions is evidenced and independently checked, keep candidate009 charged and block candidate010, admission, diagnostics, tests, and aggregate work that would depend on clearing this attempt.
