## 2. Process-incarnation-bound ownership and receipts

Do not use `id(handle)` or a numeric PID alone as durable ownership. Bind every root/handle owner and every cleanup claim to `(boot_id, owner_pid, owner_start_ticks, main_session_id, root_token, fresh_owner_nonce, handle_object_id)`. The nonce is generated once when Main registers the retained exact handle and is stored in the durable ledger; its registry entry is created atomically under the registry lock before publishing the binding. Each API call validates that its current process incarnation and exact retained object still match this registration. A forked child has a different PID/start identity and must reject inherited registry entries and copied descriptors; a process restart cannot recover a Popen object or volatile syscall receipt. Any owner mismatch, lost registry, or unresolved claim remains charged; a different process may consume an already durable result but may not perform another wait, send, or close for that owner.

All local ledger-mode cleanup callers obtain the one mutex associated with the exact root token from a registry protected by a registry-wide lock. The mutex is installed once and retained through retirement/uncertainty; no caller creates a competing mutex. Every durable event also carries a stable operation key derived from root token, owner nonce, exact handle registration, target token/identity, and operation phase. Under the interprocess ledger lock, perform readback-first replay: reread and validate the full journal; consume exactly one matching key/payload if present; if absent, append once, fsync, reread, and verify exactly one matching event; reject conflicting/duplicate payloads and remain charged. Never retry an append without that predicate.

For the root wait, hold the per-root mutex before making the one OS wait claim. Persist the claim with the owner incarnation and operation key before waiting; release the interprocess journal lock while blocking but retain the per-root mutex. Capture the exact terminal into the owner registry before appending the matching `root-wait`. The live exact owner may retry only by first reading the journal and then consuming or appending its cached receipt once. If the owner incarnation or receipt is lost before durable `root-wait`, keep the root charged indefinitely; no second wait, inferred result, signal, or retirement. The same claim/receipt rule applies if the root exits during pin acquisition.

For each target/signal, acquire the per-root mutex and interprocess journal lock, validate the exact process-incarnation owner and operation state, append/read back one `signal-intent`, check the original absolute deadline immediately before the one pidfd syscall, perform exactly one syscall, then append/read back its result before releasing the lock. This makes the send exclusive across cleanup callers. A durable success is consumed without resend. Intent without durable result and without the exact live owner's cached syscall receipt is unknown: no repeat, no later target signal, and no retirement. Same-owner receipt replay is readback-first and operation-key idempotent. A waited root is never signaled; unsupported pidfd send never falls back to numeric identity. Preserve original TERM grace, escalation, deadlines, and cleanup-error precedence.

Pin close uses the same exact owner incarnation, root mutex, operation key, and readback-first append rule. A descriptor is closed at most once by its live exact owner; cache the close result before publishing `pin-closed`. A different or restarted process may not retry close by integer descriptor. If the result/receipt is lost, leave the tree charged and unresolved. Descendant retirement requires exact terminal and pin-close evidence; root retirement follows exact root terminal, descendant retirement, no unresolved reservations, final census, and readback-verified events.
