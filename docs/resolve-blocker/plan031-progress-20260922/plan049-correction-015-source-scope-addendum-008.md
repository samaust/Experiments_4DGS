## Durable transitions and outstanding creators

Define and test the replayable root graph explicitly:

`live -> stopping -> waited -> retired`

`stopping` is a durable, capacity-charged intent. Under the interprocess ledger lock it closes admission to new descendant reservations. A reservation already durably recorded before `stopping` is outstanding, not yet included in a pinnable cleanup set. While any reservation lacks a durable creator outcome, cleanup sends no signal and retires nothing. The existing creator may complete its already-reserved create, bind its returned handle/identity, and acknowledge it; cleanup then takes a new locked snapshot and pins that exact acknowledged child. If create fails, record cancellation only when the creator can prove no child was created; otherwise retain the reservation as unresolved and charged. New reservations after `stopping` fail before the OS create call. Every retry reloads and validates ledger readback under lock; it cannot rely on a stale census or pin set.

The root wait is performed at most once through its exact retained process handle. A concurrent caller that observes the matching durable `root-wait` reuses that terminal and does not wait again. `live` can enter `stopping`; `stopping` can enter `waited` only through the exact matching handle wait; `waited` can resume descendant cleanup but is never signaled; `retired` accepts only the exact same-handle idempotent cleanup path and emits no signal or second wait. Root retirement follows all descendant retirements and requires the same recorded root terminal. Failed append/readback, pin, signal, wait, or retirement leaves the affected records charged; same-handle retry is allowed only when exact open descriptors/handles remain valid, otherwise it fails closed without reopening by numeric identity.

The selected creator inventory is a required plan gate, not an assumption: statically enumerate every process/thread creation entrypoint reachable from the nine authorized files and fixtures and prove each process creation uses the reserve-create-bind-ack protocol before any OS create. The current inventory candidates include `Owner.run`/`os.posix_spawn`, `create_owned_process` call sites, supervisor `subprocess.Popen`, capture `Popen`, native owner-thread creation, and fixture wrappers. Update that inventory during exact-source review. If an unmediated creator is reachable, do not claim this protocol closes creation; stop for another narrowly scoped reviewed plan amendment. No new admission is permitted after `stopping`.

## Pinning, signaling, deadline, and retirement

For a live root, pin its exact PID and each acknowledged live descendant with pidfds while the processes are present; recheck boot ID, PID, start ticks, PPID/creator ancestry, PGID, and ledger token. For a previously waited root, reuse only the exact retained handle and matching durable wait terminal; never reopen or signal the root. A missing pidfd facility, unsupported pidfd signal operation, identity mismatch, ambiguous/untracked group member, unacknowledged reservation, or escaped/unaccounted member leaves the tree charged and blocks signaling or retirement. Do not fall back to numeric PID/PGID signals.

The cleanup census is evidence about the selected managed process group at that instant, not a claim that the OS prevents arbitrary code from forking or changing groups. The exact-source audit must show all selected managed creation entrypoints are mediated by the durable reservation protocol. Every census member must map to an acknowledged exact ledger identity and retained pin. Any unknown member or evidence that a managed child escaped the group blocks retirement and keeps its charge. Re-census and reload the ledger after waiting/signals and immediately before retirement; group emptiness alone never substitutes for exact terminal evidence of each registered member.

Use only pidfd-bound signaling for ledger-mode targets. Preserve the original TERM grace and absolute cleanup deadline. Check the same absolute deadline immediately before every pidfd TERM/KILL send and before every deadline-bounded wait/census operation. Do not send any signal after expiry and do not extend or restart the deadline. Track per-target signal progress while retaining the same open pidfds. A retry may repeat an idempotent signal only through the same still-open pidfd to the same unresolved identity; it must never signal a closed/reopened numeric identity. If exact retry state cannot be established, leave the tree charged. At the existing escalation point, send KILL only to unresolved pinned targets, excluding an already waited root. Preserve existing cleanup-error precedence and return semantics. Unsupported pidfd operations fail closed.

Retire descendants in the existing required order only after exact pidfd/process-handle terminal proof and durable ledger readback. Retire the root last, only with the matching root wait, all managed descendants retired, no outstanding reservations, and repeated final ledger/group census consistent with empty membership. Close pins after durable retirement; if close status is uncertain, retain the accounting uncertainty rather than blindly closing a potentially reused descriptor. The already-retired exact-handle repeat path is signal-free. The legacy no-ledger branch remains byte-for-byte equivalent in behavior and retains its existing group signals, waits, deadlines, return values, and cleanup precedence.
