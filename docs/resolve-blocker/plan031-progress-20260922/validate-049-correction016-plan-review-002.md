# Independent review of revised Plan049 correction016

**Verdict: not clear for six-lane runtime dispatch.** The revised plan gives lanes 5 and 6 real sidecar checks and preserves the final serial diagnostic and aggregate order. Its asserted tightest live charge is wrong, and its sidecar replaces the capture/runner identity anchor required by current source. These are concrete design blockers, not a reason to relax the original deadlines or silently substitute serial tests. Static lane preparation remains possible under the existing stop rules.

I reviewed the revised [correction016](plan049-correction-016.md), [Plan049](../../../plans/plan_049.md), [correction015](plan049-correction-015.md), [correction008](plan049-correction-008.md), the [wrapper validation](../plan031-session-proof-wrapper-20260923/validation.md), and the current `s1_helper_session.py`, `s1_validation_contract.py`, `launch-049-exec.py`, capture, runner and relevant helper tests. This was a static review only: no project import, test, launch, source edit, status edit, prompt read or commit.

## Blocking findings

1. **F1's real Owner thread invalidates the proposed peak table.** `Session.start` calls `_thread.start_joinable_thread(self.owner.run, daemon=False)` in `s1_helper_session.py:893`; `Owner.run` then creates the work and sample helper processes. At the claimed four-worker F1 peak, even ideal single-thread counts are root 1 + fault workers 4 + Owner 1 + helpers 2 = **B 8, H 0, charge 9**. The table states B 7/charge 8 because it omits Owner. Plan047 counts every actual task-owned thread in B and reserves `max(1,H)`. This topology violates `≤8` at a required F1 path before considering native, tool or writer threads. A cross-process gate would correctly reject the second helper; it cannot make the four-worker peak admissible. The same issue may occur in F10 or any other live `Session` path. A revised schedule could retire one fault worker before F1's two-helper phase, leaving root 1 + workers 3 + Owner 1 + helpers 2 = B 7/charge 8, but that is no longer six simultaneous test contexts at that peak. It must prove meaningful overlap during other test intervals and avoid calling parked or completed lanes active. If all six contexts must remain active through that peak, a different topology or explicit cap change is needed.

2. **The proposed sidecar has no compatible current ownership anchor.** The design says `parallel_focus` will `execve` a sidecar directly in the driver root and use `owned_workload()` for live creation gates. Current `_launch_anchor` in `s1_helper_session.py:457–490` locates a `python -B -` stdin runner, requires its parent to have the exact capture command and validates the runner's `stdin.py` descriptor; `owned_workload()` calls that anchor and `no_timeout_launch()` on each check. Current driver accepts only `diagnostic|aggregate` and constructs the capture command (`launch-049-exec.py:52–104`); current contract requires that same command and capture output shape (`s1_validation_contract.py:531–595`). A direct sidecar cannot pass these predicates merely by adding a `parallel_focus` branch or a creation lock. The plan needs an exact alternative root/command/stdin/log/output/source proof that retains equivalent identity and provenance checks, with every affected function and file listed and independently reviewed. Otherwise no fault worker can safely use the existing capacity gate.

3. **A file lock is insufficient for cross-process ownership.** `INVOCATION` and its `RLock` are process-local (`s1_helper_session.py:372–390`); `owned_workload()` combines the current process's registry with its observed descendant tree. Four workers do not share that registry. The proposed atomic file lock can serialize creation, but does not by itself preserve a returned PID before a fallible registration, track uncertain ownership across sibling workers, or retain a detached/reparented child after it leaves the root ancestry tree. The plan names registration and retirement gates but does not specify the durable shared identity/uncertainty state, crash recovery, lock ownership, and retirement proof needed for every reachable creation seam. The source review it proposes must cover this before claiming continuous `≤8`, including the source's Owner thread and temporary sidecar worker creation.

4. **Six useful test contexts are conditional, not demonstrated.** The two root tasks have specific useful isolation/contract checks and can overlap four fault workers without adding threads if their work yields in bounded chunks. That is a substantive improvement over the prior documentation-only lanes. Yet the plan has no proven nonblocking implementation or exact selector IDs/receipts, and the F1 peak requires a reduced worker overlap under the retained cap. The root checks must produce independently verifiable failures and receipts during worker execution; merely polling artifacts while fault workers are blocked does not establish six active checks. None of these focused receipts replaces the required complete HelperSessionTests selection or final 249-method/1,028-callback aggregate.

5. **Temporary source and launch scope need exact authority.** The revised plan proposes a sidecar, a new driver/contract mode, `s1_helper_session.py` identity and creation changes, and a `supervisor.py` registration change. Correction015 opened supervisor for F2 only and froze `s1_helper_session.py`; correction008 pins the fixed capture/runner command and session-bound proof. The new user instruction directly supports a temporary scheduling exception to one active subagent and serial focused tests, while preserving the stated caps, behavioral deadlines and scope restrictions. It does not by itself prove that altered identity/launch predicates or new source paths preserve those restrictions. Before implementation, specify the exact temporary predicates, source paths and tests in a reviewed correction or identify any further authorization needed for a changed authority/trust model. Keep the original diagnostic/aggregate path byte-for-byte in behavior and validate restoration against a hash-pinned pre-parallel baseline.

## C1–C3 and return to serial order

The saved wrapper validation still blocks every live Plan049 attempt: exact tool-return escrow/readback, paired actual-boundary monotonic timestamps and an independently accepted same-session procedure are not established. A verified platform facility that meets the existing contract would need no new user authorization. The proposed alternative—causal timestamp bounds and a separately charged writer process—changes Correction008's exact evidence meaning and no-new-process trust topology; **specific new user authorization is warranted for that alternative**, after the procedure, transport/clock semantics, failure handling and source delta are made concrete and independently reviewed. The six-task scheduling authorization is not that trust amendment. No runtime launch may use the current proposal as a workaround.

The planned inverse patch and fresh baseline comparison are directionally sound: temporary parallel mechanics should be removed after worker/ownership reconciliation, then substantive F1/F7/F8/F10 patches should be integrated one at a time. However, a source change made to support the sidecar invalidates those lane receipts for final current-source acceptance. Preserve the original 0.15/0.3/0.5, 2/1, W/C and all other behavioral assertions; keep `B+max(1,H)≤8`, 150GiB artifacts, 64MiB memo, 42 scenarios, six scripts and full 510/340/170 guards. Only a new complete Main-owned serial diagnostic and one unchanged current-source aggregate can establish B1–B4 after restoration and independent exact-source review.

If that cannot be shown, identify the exact additional cap or topology decision rather than declaring the current topology executable.
