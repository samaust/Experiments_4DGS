## 2. Root wait ownership and duplicate-safe event replay

All exact-handle calls to ledger-mode `stop_group` acquire a per-handle in-process mutex keyed by the root token before consulting or mutating wait/signal state. The mutex object is created once in the existing `stop_group` lifecycle registry and retained until durable root retirement; the registry entry is not evicted on uncertainty. No caller invokes wait or changes cleanup state without that mutex. The interprocess ledger lock additionally serializes every durable event check/append and every signal transaction across processes.

Use stable operation keys formed from root token, exact handle object ID, target token/identity, operation, and signal/phase. For any event append, hold the interprocess lock, reread and validate the complete journal, and first search for the unique exact operation key and payload. If found once, consume its event; if absent, append once, fsync, reread the journal, and verify exactly one matching event. If present with a different payload or duplicated, fail closed and keep the root charged. A readback error is retried only by rereading and applying this predicate before any append; never blindly append a duplicate.

Before the one OS root wait, durably claim the exact root-wait operation while holding both the per-handle mutex and interprocess lock. Release only the interprocess lock for the blocking wait; keep the per-handle mutex. Capture the exact terminal in the retained handle registry before persisting `root-wait`. If the wait returns but append/readback fails, the same live owner retries readback first and either consumes the one matching event or appends that exact cached receipt once. A contender cannot observe or wait concurrently because it cannot acquire the mutex. If the owning process/handle registry is lost before an exact root-wait is durable, remain charged in wait-claimed state forever; do not wait again, infer a terminal, signal the root, or retire it. The root that exits during pin acquisition uses the same single-flight and receipt process. An already durable wait is replayed by exact operation key and handle ID; `root-retired` cannot precede this proof.

## 3. Exclusive per-target signal transaction

For every target and signal, derive one stable operation key. Under the same in-process root mutex and interprocess ledger lock, reread the full ledger and require no existing conflicting operation. Append/read back `signal-intent` before the syscall. Keep the interprocess lock held from the intent readback through the immediate original-deadline check, the single pidfd send, and the matching result append/fsync/readback. This critical section prevents another cleanup caller from sending the same target/signal concurrently. Check the original absolute deadline immediately before the syscall. Do not hold an interprocess lock while waiting for process termination or the TERM grace interval.

If the send succeeds and the matching `signal-sent` event is durable, later callers consume that exact event and never resend. If the syscall fails, the owner persists a definitive failure only if the syscall contract establishes no signal was sent; otherwise record/retain an unknown outcome. If the process/lock owner disappears after intent and before a durable result, the intent is unknown: no caller sends that signal again, no later target signal is sent, and the whole tree stays charged. If an append write/fsync/readback fails after a successful send, the next same-handle caller takes the locks and rereads first; it consumes the uniquely matching success event if present. If no result event is present, the still-live owner may use its exact retained syscall receipt to append that same result once, with duplicate-key replay. If no such owner receipt is available, outcome remains unknown and cleanup stops. TERM/KILL use separate operation keys; KILL remains at the original escalation point and is permitted only for a target whose TERM success and live state are durably known. A waited root is never signaled. No numeric signal or fallback is allowed.
