## Blocking source findings

1. **Ordinary nonblocking wait is made terminal uncertainty.** `s1_helper_session.py:775-808` durably claims the one wait before calling `os.waitpid(pid, flags)`. When `flags=os.WNOHANG` and the child is still live, POSIX returns `(0, 0)`. Lines 793-795 append `operation-uncertain` and raise. This is an ordinary, expected poll in `Owner.reap_child` (`:1792-1795`) and the unchanged sentinel loop in `test_vipe_benchmark_supervisor.py:1419-1423`. The new code changes their deadline/order/error behavior and makes a subsequent terminal wait impossible because the claim is now unresolved. The normal no-result poll must remain nonterminal and replayable without claiming a completed OS wait.

2. **Direct descendant wait retirement contradicts replay.** `_wait_job_handle` and `wait_owned_pid` emit `descendant-retired` directly when no pin is open (`s1_helper_session.py:765-771,803-807`). `_job_state` first rejects *any* operation for that token in state `claimed` (`:574-575`) and only later describes a `fresh_wait` path that requires the same wait operation to remain `claimed` (`:578-585`). Consequently an actual direct descendant retirement row is rejected before its intended branch can run. Nested fixture child waits use this path, so strict replay and owner closure cannot pass.

3. **A cap or verified rollback does not stop other ledger writers.** In `append_job_event`, `poison('cap',False)` at `:641-643` and `poison('rolled-back',False)` at `:672-675` set only the process-local `JOB_LEDGER_POISONED` variable. They do not place the persistent lock poison marker that `job_ledger_events` and other processes check. Another process using the same sidecar can therefore append a smaller row after one writer hits the 8,388,608-byte cap or rolls back a failed write. Addendum021 requires even a verified rollback to stop the attempt and prohibit further append/admission/retirement; this source does not enforce that across the multiprocess owner tree. The per-row `S+L` check correctly prevents an intentional over-cap committed line, but it is not an attempt-wide stop.

4. **The purported closed event schema still admits arbitrary result objects.** `_JOB_EVENT_FIELDS` lists event names and top-level keys, but `_job_event_data` checks `signal-result.result` and `pidfd-closed.result` only with `type(...) is dict` (`s1_helper_session.py:222`); `_job_value` permits arbitrary nested keys and values subject only to generic depth/length bounds. `_job_state` copies these results without checking the expected `sent/error` or `closed/error` shapes (`:536-561`). This does not meet Addendum021's required primitive/closed nested types and exact failure variants. Similar `signal-intent.target` validation is only `dict` at `:221`, although replay later compares it with a pin. A source-level exact event/field/emitter table remains incomplete.

5. **The candidate is not fully immutable at create.** `_prepare_owned_candidate` freezes the effective environment but retains the original `args[1]` argv object for `os.posix_spawn` and `os.execve` (`s1_helper_session.py:318-322`). The post-reservation check reconstructs a descriptor, then passes that same mutable argv object to the syscall (`:1460-1465`; driver `launch-049-exec.py:334-336`). There is no frozen OS-byte argv tuple copied from the validated rendering. This does not establish Addendum021's same immutable materialized bytes at reservation and immediately before create, particularly for a shared mutable list.
