## 2. Single-flight exact root wait

Under the interprocess ledger lock, a root in `stopping` can transition to `root-wait-claimed` exactly once, binding the claim to the exact retained process-handle object identity and a unique claim token. The caller must also hold the existing per-handle in-process single-flight lock before claiming. It releases the interprocess ledger lock before the potentially blocking wait but retains the per-handle lock. No contender calls wait while that lock is held. A contender that later acquires it reloads the ledger: if `root-wait` is durable, it consumes that exact terminal; if the original owner has a retained in-memory wait receipt but its append/readback failed, it retries only that receipt's durable append; otherwise it does not wait again.

The wait owner captures the exact return/terminal result once and retains it in the handle's lifecycle state before appending `root-wait`. If append/readback fails while the owner remains alive, same-owner retry may append/read back that exact receipt without another wait. If the owner/caller disappears before `root-wait` is durable, the root remains charged in `root-wait-claimed`; no second wait, inferred terminal, signal to the root, or retirement is allowed. This is a deliberate fail-closed unresolved state. A root that exits during pidfd pin acquisition follows the identical claim/single-flight path. A contender never treats `stopping` or `root-wait-claimed` itself as proof of wait completion. The exact `root-wait` terminal is durable before transition to `waited`; `waited` permits only descendant cleanup/finalization and never root signaling or another wait.

The replay graph is `live -> stopping -> root-wait-claimed -> waited -> retired`, with `root-wait-claimed` able to remain charged indefinitely if its exact owner receipt cannot be recovered. Already-durable `root-wait` can be replayed as `waited`; already-durable `retired` permits only addendum006's exact-handle, signal-free idempotent path. Descendant reservation cancellation, binding, creator acknowledgment, terminal, and retirement remain as addendum008 specifies. Root retirement follows durable retirement of every descendant and exact-handle terminal matching.

## 4. Replay-safe per-target signals and descriptor retirement

For each exact pidfd-pinned target, persist a `signal-intent` event binding root token, target token/identity, signal, original absolute cleanup deadline, and sequence before sending. Immediately check the unchanged deadline before every send. After a successful syscall, persist and read back `signal-sent` before sending to another target. A syscall error, ambiguous outcome, failed append/readback after a send, or owner loss leaves that target's outcome unknown and the tree charged; send no later signal to another target and never repeat a signal whose outcome is unknown. A durable `signal-sent` is skipped on retry; an unsent target can proceed only after fresh locked ledger verification and an immediate deadline check. KILL is allowed only at the original escalation point, for an exact target whose TERM success and still-live terminal state are durably known, and through the same retained pidfd. A waited root is never signaled. No signal operation falls back to numeric identity.

After exact terminal proof, persist `target-terminal` and read back before retiring the target. Close its retained pidfd once. A successful close is recorded by a durable `pin-closed` event before root retirement. If close outcome is uncertain, do not retry close by descriptor number (it may have been reused), do not claim successful pin retirement, and keep the tree charged/unresolved. If recording `pin-closed` fails after a successful close, retain a local immutable close receipt and retry only its ledger append; if that receipt/owner is lost, the tree remains charged. Thus no descriptor ambiguity is hidden by durable process retirement.

All signal, wait, census, ledger, and close transitions retain the existing original cleanup-error precedence and absolute deadline. Check the deadline immediately before each deadline-bounded wait/census/send; do not extend it. TERM grace remains unchanged. Any unresolved state remains capacity-charged and blocks cleanup admission. The legacy no-ledger path retains original signals, waits, deadlines, return values, and cleanup precedence.
