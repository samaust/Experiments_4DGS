The D8/D11 setup worker produces `plan069-depth-setup-result/v1` with the pinned archive, extracted native entry record plus complete extracted source manifest and digest, exact asset records, received bytes and elapsed time. D11's native folder path stages all accepted frames as lossless PNG and invokes the pinned CLI once; the existing D11 adapter then consumes the saved raw `.npy` predictions in exact input order. Actual dispatch requires a passing independent source-review receipt and the shared ledger's single-use reservation. The runtime and commercial admission receipts must be produced only after installed dependency, model-load and memory checks pass.


Both native entry gates rehash the complete extracted source tree and archive, including imported modules and configuration files, before model execution. Setup snapshots the tree immediately after extraction and verifies it again before publishing completion. Native Python bytecode writes are suppressed so import qualification and inference cannot add caches to that verified tree.

Each native entry performs a CPU package metadata qualification before model loading. The qualification records the exact selected interpreter path and bytes, installed package metadata, and package digest. D8 requires its native Torch range and pinned utils3d revision; D11 requires the native package pins using PEP 440 version equality (for example pyarrow 18.0 and 18.0.0 are equivalent). This package gate does not constitute a successful CUDA model-load or memory qualification.

The D11 CLI initializes seed 2025 once per folder run. Its ordered images share the native RNG stream; the seed argument does not establish an independent RNG reset per image. The child evaluation process uses the selected interpreter environment through PATH, offline assets at DEPTH_ASSETS_DIR, and bytecode suppression. Actual native processes inherit the reserved worker process group so the shared supervisor recognizes their GPU ownership. A native timeout or interruption stops that entire reserved group; its outer supervisor records the failed attempt. CPU fixtures use a separate native group. Both paths stop the CLI and its evaluation child together. The saved result retains the source manifest and entry package qualification.


The setup worker now prepares a separate environment for each candidate before acquiring model assets. It binds the retained E5 Python 3.11 interpreter and existing uv binary. D8 selects Torch 2.4.1/cu124 and torchvision 0.19.1/cu124, below the native Torch ceiling; D11 selects its exact native dependencies and cu128 wheels. The common environment helper creates the venv without Python downloads, resolves a hash lock, installs that lock through the existing metered HTTPS proxy, checks dependencies offline, and hashes the installed distribution inventory. D8's pinned utils3d archive uses the direct transfer meter and an offline local package installation; its archive hash, revision and extracted source manifest bind the installed package provenance.

Environment transfers and storage share the candidate's original setup allocation and cumulative 110/210 GiB limits. The environment phase reserves the exact model asset bytes before resolving packages. A dependency closure that cannot fit those limits blocks setup; no larger allocation, new attempt or unmetered network path is selected. Actual provisioning remains unrun, so CPU fixtures do not establish that either resolved closure fits. Native entry requires the prepared venv's absolute invocation path and identical package qualification snapshot. Both setup results include the pinned weight revision.

D11 has a dedicated admitted worker (`basketball_vipe_depth_d11_maps.py`) and dispatcher (`basketball_vipe_depth_d11_dispatch.py`). The dispatcher requires an explicit independently reviewed source receipt, the exact accepted context 003 and its ledger charge, completed pinned setup, and a `plan069-depth-D11-qualification/v1` bundle. Both the bundle and runtime receipt bind the prepared environment's original absolute invocation path. One native folder call covers the 60 anchors and 196 additional clip identities, with frame 175 reused in each clip. The `plan069-D11-maps-result/v1` receipt binds the native folder result, and validation compares saved raw arrays with native predictions.

D11 outputs retain `relative_log`, `metric_scale=not_applicable` and `engineering_eligibility=not_applicable`; no metric fit is generated. `basketball_vipe_depth_d11_publish.py` uses the shared publisher only after a successful cleanup-confirmed GPU ledger finish. Publication renders four 50-frame clips with the shared whole-clip diagnostic normalization and charges CPU time to the approved allocation. These entrypoints and their provenance gates have CPU fixture coverage; actual runtime qualification and execution remain unrun.
